# 면접 진행 코드 다시 읽기

분석 기준은 manifest의 공개 원본과 후속 패치를 적용한 코드입니다. 이번 PR은 역할과 비용을 파악하는 단계이며 서비스 책임을 분리하는 리팩터링은 수행하지 않았습니다.

## 요청 흐름

1. `InterviewService.chatInterviewer`에서 사용자와 면접을 조회하고 소유자를 확인합니다.
2. 시간과 현재 턴을 확인해 서버의 마지막 질문 조건을 정합니다.
3. `createQuestion`에서 최근 질문·답변과 선택한 문서, 상태 저장소의 주제를 모아 AI 요청을 만듭니다.
4. AI의 종료 판단과 서버의 마지막 질문 조건을 OR로 결합합니다.
5. 현재 턴을 늘리고 생성한 질문을 반환합니다.

원본 코드는 AI가 반환한 종료 신호를 서버의 false 값으로 덮어쓸 수 있었습니다. 이관 PR의 회귀 테스트는 AI 종료와 서버 제한이 서로 다른 경우를 확인합니다.

## 의존성에서 읽을 후보 찾기

정적 import 기준 InterviewService의 fan-out은 22입니다. 데이터 조회, AI 요청, 상태와 진행 제어의 의존성을 함께 갖고 있어 역할을 나눌 후보입니다. 이 수치에는 타입과 엔티티 import가 포함되므로 호출 횟수나 성능 비용으로 해석하지 않습니다.

ORM 엔티티 사이의 순환 그룹도 확인했습니다. 양방향 관계 매핑이 포함되므로 순환 자체를 제거 목표로 잡기 전에 런타임 의존성인지 타입·관계 선언인지 나눠 읽겠습니다.

## TTL 갱신 비용 확인

KeySetStore는 addToSet에서 스케줄러의 기존 키를 remove한 뒤 push합니다. MinHeapScheduler.remove는 findIndex로 키를 찾습니다. 새 키처럼 기존 항목을 찾지 못하는 경우 전체 힙을 확인하므로 O(N) 탐색이 발생합니다.

실제 스케줄러 소스를 TypeScript로 변환해 없는 키의 remove를 실행했습니다. 비교 횟수는 힙 크기 100, 1,000, 10,000, 50,000에서 각각 같은 수로 증가했습니다. 설정과 워밍업을 제외한 일괄 호출의 평균 시간도 함께 기록했습니다.

| 힙 항목 수 | 비교 횟수 | 라운드별 평균의 중앙값 |
|---:|---:|---:|
| 100 | 100 | 0.69μs |
| 1,000 | 1,000 | 4.98μs |
| 10,000 | 10,000 | 47.76μs |
| 50,000 | 50,000 | 238.05μs |

Node 22.14.0, macOS ARM64. 조건별 워밍업 100회, 1,000회씩 7라운드입니다. 값은 API 지연이나 개별 호출의 p95가 아니라 라운드별 평균의 중앙값입니다. 실제 활성 키 수와 갱신 빈도는 아직 수집하지 않았습니다.

```sh
python3 scripts/prepare.py
# checkout에서 pnpm install --frozen-lockfile 실행 후
node scripts/bench-scheduler.cjs checkout results/scheduler-remove-baseline.json
```

다음에는 활성 키 수와 갱신 빈도를 확인한 뒤, 키별 힙 인덱스를 추가할 이점이 있는지 검토하겠습니다. 인덱스를 도입한다면 swap·pop·remove 때 인덱스가 유지되는지와 동일 키 TTL 갱신을 먼저 테스트해야 합니다. 이슈 #2에서 이어갑니다.
